# Analysis and plotting

Software MUST be open source. If a reader cannot read the code that produced a number, they cannot check the number, and the result is a claim rather than a measurement. The requirement is about verifiability rather than licensing preference.

The same rule applies to machine learning. A trained model is part of the analysis, so training data, training code, and weights must all be open. A network whose weights are published without its training set is still a black box, because its failure modes cannot be predicted or tested.

## Software versions and environments

An analysis is defined by its code and by everything the code was standing on. Numerical results move between library versions, and results that depend on the GPU or the thread count are more common than most of us would like.

Publish the pinned environment, not a list of package names. A lock file, a conda environment export, or a container image are all acceptable. A `requirements.txt` with unpinned versions is not, because it will resolve differently in a year and silently produce different numbers.

Containers are a good option here, and they provide what the abstract asks for: a complete runnable record that a reader can execute without reconstructing anyone's laptop.

## Parameters and random seeds

Every parameter that affects the output has to be recorded, including the ones chosen by hand at the terminal and never written down. In practice this means the analysis should be driven by a configuration file that is published with the result, so there is no gap between what was run and what was reported.

Stochastic methods need their seeds. Reconstruction algorithms with random initialization, stochastic gradient methods, dropout, and Monte Carlo sampling all give different answers on re-runs, and publishing the seed makes a run exactly repeatable.

Repeatability is only the starting point. If the result changes meaningfully when the seed changes, then reporting one seed hides the problem, so report the spread across seeds and treat the variation as an uncertainty on the result.

## Notebooks and scripts

Notebooks are excellent for communicating an analysis and poor at guaranteeing it. Cells can be run out of order, and the stored output can come from code that no longer exists in the file.

Publish notebooks with their outputs cleared and a test that runs them top to bottom. If a notebook does not produce the published figure on a clean run, it does not document the analysis.

For anything that takes more than a few minutes, move the computation into a script or module with the notebook calling it. This makes the analysis testable, keeps it out of the presentation layer, and lets the expensive part run somewhere other than a laptop.

## Figures as derived data

Plotting an image or chart is fine, as long as it links back to the raw experimental data.

A figure is a highly compressed form of a result, and often the only form a reader will see. It is also a data product, produced by code, from an input, and it should be treated that way. Every published figure should be generated by a script that takes the archived data and emits the file, with no manual steps in between.

Manual steps are a common source of error here. Cropping in an image editor, adjusting levels by eye, and pasting panels together by hand all leave no record, cannot be checked, and cannot be redone when a reviewer asks for a different scaling. If a figure cannot be regenerated by running one command, the link back to the data is already broken.

This also solves a practical problem. Reviewers ask for changes, and a scripted figure can be regenerated in seconds with the numbers guaranteed to still match the data.

## Colormaps and scaling

Use a perceptually uniform colormap. The rainbow and jet maps introduce visual features that are not in the data, hide features that are, and are unreadable to colorblind readers ([Crameri et al., *Nat. Commun.* 2020](https://doi.org/10.1038/s41467-020-19160-7)).

Match the map to the data. Sequential data takes a sequential map. Data with a meaningful zero, such as DPC, strain, or a difference image, takes a diverging map centered on zero. Orientation and phase are cyclic and need a cyclic map, or the discontinuity will read as a physical boundary.

State the scaling. Intensity limits, whether the scale is linear or logarithmic, and any gamma applied. Clipping the display range is a normal and useful thing to do, and it becomes misleading only when it goes unstated. The same holds for smoothing and denoising: if a filter was applied before display, say which one and with what parameters, and show the unfiltered data somewhere.

## What a figure must disclose

Every figure should carry, in the caption or the metadata:

- A scale bar, with the calibration it came from
- Modality and the key acquisition parameters, including dose
- Colormap and intensity range
- Any filtering, smoothing, or background subtraction applied before display
- Whether the data shown is one field of view or an average, and over how many
- An identifier resolving to the archived dataset and the code that made the figure

The last item carries the most weight, since every other one can be reconstructed by a reader who has the data and the script.

The phrase "representative micrograph" deserves particular scrutiny, because it usually means one image was chosen from many, by a person, using criteria that were never written down. If the full set is published, the reader can judge what representative meant. See [publishing](publishing.md) and [chain of custody](chain-of-custody.md).
